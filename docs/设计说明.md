# 课小帮 · 设计说明（一期）

> 作品名称：课小帮 —— 面向大学生家教的一对一智能备课与学情闭环系统
> 队伍：备课汪汪队 ｜ 赛道：教育教学 ｜ 版本：v1.0（2026-10）

## 一、产品定位

市面上的 AI 备课工具（智能教案、课件生成等）基本面向**班级授课**场景，输出的是统一进度的教案与课件。而一对一补习的核心诉求是：针对**某一个学生的具体薄弱点**，快速组织一节 45~90 分钟的课，并在课后向家长交代清楚。

课小帮聚焦这个被忽略的场景，把家教老师的单次授课拆成四个环节并全部覆盖：

| 环节 | 老师的真实痛点 | 课小帮的做法 |
| --- | --- | --- |
| 备课 | 找题、配题、分层耗时数十分钟 | 依据学情档案自动生成讲练素材包，支持换题与导出 |
| 授课 | 课上临时想不起来该提醒什么易错点 | 每个知识点附带讲解要点与易错提醒 |
| 记录 | 课后凭记忆写反馈，容易遗漏 | 课后对题目一键三态勾选，5 秒完成记录 |
| 反馈 | 给家长发消息要斟酌措辞 | 自动生成三种语气的家长反馈话术与可打印报告 |

**闭环价值**：本次课的勾选结果会写回学情档案，成为下次备课的推荐依据。用得越久，推荐越准。

## 二、用户与角色

- **主用户（一期）**：大学生家教 / 兼职教师，一人管理多名学生
- **学生（二期）**：课堂互动与错题回顾
- **家长（二期）**：查看学情报告、确认回执

一期只做老师端，理由是：闭环的驱动者和使用者都是老师，先把老师的体验做扎实，再向两端延伸。这不是功能缺失，是刻意的聚焦。

### 老师账号与数据隔离（一期实现）

一期提供老师登录页，但定位必须说清楚：**它是身份标识，不是安全认证**。

| 能力 | 一期 | 二期 |
|---|---|---|
| 身份识别 | 输入姓名即进入，同名视为同一账号 | 微信登录 / 手机号验证码 |
| 数据隔离 | 按老师 ID 分区存储（`students.v2.<teacherId>`），各看各的学生 | 云数据库按 teacherId 查询 |
| 密码校验 | 无 | 有 |
| 跨设备同步 | 无（数据在本机浏览器） | 有 |

二期只替换存储实现，`store.js` 对外接口不变，页面与生成引擎无需改动。

同时预置一个**演示账号**（含 3 位学生、累计学情），解决答辩现场"从零录入看不到闭环效果"的冷启动问题。

## 三、技术架构

```
┌─────────────────────────────────────┐
│  前端层（可替换）                    │
│  一期：Web / H5        二期：微信小程序│
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  AI 能力层                           │
│  备课生成 / 学情分析 / 反馈话术生成   │
│  一期：知识点体系 + 题库 + 规则引擎   │
│  二期：接入大模型生成，保留教师审核   │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  数据层                              │
│  学科知识点树 / 学生档案 / 学情记录   │
│  一期：浏览器本地存储  二期：云数据库 │
└─────────────────────────────────────┘
```

**核心设计原则：前端可替换，能力层与数据层独立于前端。**

因此一期用 Web 端快速验证商业模式与交互流程，二期迁移小程序时，只需重写界面层，业务逻辑与知识点数据可整体复用。

## 四、核心技术资产：学科知识点体系

分层出题与薄弱点归因不是靠大模型"感觉"，而是建立在结构化的知识点数据之上。

一期已完成**人教版小学数学四年级下册**：9 个单元、35 个知识点，每个知识点包含：

- 难度分级（基础 / 进阶 / 变式）
- 讲解要点（教师可直接使用的授课提示）
- 易错标签（如"小数点移动方向搞反""末位对齐而不是小数点对齐"）
- 配套题库：已覆盖 11 个重点知识点 × 3 档难度 = 33 道题，含答案与解析，**全部经过人工核对**

这套数据结构决定了系统能否真正做到"分层"和"归因"，也是后续扩展其他学科的基础模板。

### 按「学科 + 年级 + 册次」解耦，支持横向扩展

知识点数据按教材（syllabus）为单位组织，每份教材独立注册：

```
教材 key：math-g4b = 数学 · 小学四年级 · 下册 · 人教版
├── units[]     单元 → 知识点（含难度、讲解要点、易错标签）
└ questions{}   知识点 → 题目（基础/进阶/变式三档）
```

页面与生成引擎只面向「当前教材」取数，**不写死任何年级**。因此新增一个年级或学科时，只需新增一份同结构的数据文件并注册，其余代码零改动：

1. 新建 `data/knowledge/syllabus-<学科>-<年级><册次>.js`
2. 调用 `KB_Syllabus.register({ key, subject, grade, term, textbook, levels, units, questions })`
3. 在 `index.html` 引入该文件
4. 在 `app.js` 的 `GRADE_SYLLABUS` 中加一条「年级 → key」映射

**当前接入情况**：人教版数学四年级下册（完整知识点树 + 题库）。其余年级在选择时会明确提示"该年级知识点体系待接入，暂按已接入教材推荐"，**不做假装适配**——未接入的年级若强行套用四年级知识点，会生成错误的教学内容，是本项目明确规避的设计红线。

## 五、生成策略：为什么演示版用规则引擎

大模型生成数学题存在**答案错误、难度失控**的风险，直接给老师用会出教学事故。因此采取分阶段策略：

- **一期（当前）**：由「知识点体系 + 题库 + 规则模板」离线生成。内容 100% 可解释、可追溯、答案准确，能完整演示闭环。
- **二期**：接入大模型生成题目与讲稿，但生成结果须通过**答案自洽性校验 + 知识点对照**，再经教师确认后入库。

代码层面，`generatePlan` 与 `buildFeedback` 是两个独立函数，替换为模型调用时界面层无需任何改动。

## 六、数据模型（简化）

```
Student {
  id, name, grade, traits, parentStyle,
  mastery: { 知识点ID → 掌握 | 模糊 | 薄弱 },
  lessons: [ { date, kpIds, results:{ 题目ID → 掌握|半会|不会 }, note, summary } ]
}
KnowledgePoint { id, name, unit, level, tip, errors[] }
Question { id, kpId, level, stem, answer, solution, errorTag }
```

## 七、数据隐私

学生学情属于未成年人敏感数据，系统遵循：

- 数据仅用于该学生的学习跟踪，不用于模型训练
- 一期数据存于教师本人设备，不上传服务器
- 家长可随时导出或要求删除全部记录
- 二期接入云端时采用加密存储与按教师账号隔离

## 八、效果量化（待执行）

计划邀请 5~10 名有家教经历的同学试用，记录：

- 单次备课耗时：使用前 vs 使用后
- 课后反馈撰写耗时
- 教师满意度与"是否愿意继续使用"

用真实数据替代主观描述，避免"从数十分钟压缩到几分钟"这类无法验证的说法。

## 九、演进路线

- **一期（已完成）**：Web/H5 端，四步闭环跑通，云端部署可访问
- **二期**：微信小程序化、云数据库多端同步、接入大模型生成与校验、课堂互动模板
- **三期**：多学科知识点体系扩展、学情预测与知识点掌握度曲线

## 十、运行方式

- 本地：双击 `app/index.html` 即可（数据以 JS 内联，无需服务器）
- 本地服务：`python -m http.server` 托管 `app/` 目录
- 公网：云端部署 `app/` 目录，获得分享链接
